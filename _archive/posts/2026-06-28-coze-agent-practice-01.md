去年我们团队参加百度 Apollo 自动驾驶比赛，核心任务是在 Apollo 开源工程的基础上做二次开发，完成特定场景下的自动驾驶功能实现。Apollo 是一个百万行级别的 C++ 工程，文档分布在 GitHub 仓库的各个角落——有 Markdown 说明、Doxygen 注释、代码里的头文件、以及官方发布的 PDF 白皮书。新队员上手光读文档就要一两周，更别提在开发时快速定位到具体模块的代码逻辑。

当时扣子刚出知识库功能不久，我试着用它搭了一个 Apollo 工程知识库智能体，把整个 Apollo 文档系统喂进去，让它变成本队的技术问答助手。结果这个东西最后成了我们比赛过程中使用频率最高的工具，没有之一。

这篇文章就围绕这个实践展开。

### 为什么选扣子而不是本地方案

做 Apollo 工程分析，最直接的思路是在本地搭一套 RAG 管道——LangChain + Chroma/FAISS + 本地 Embedding 模型，方案很成熟。但有几个现实问题：一是比赛期间团队所有成员分散在不同机器上，本地部署的 RAG 服务要么只能一个人用，要么需要额外搭服务器，维护成本不低；二是 Apollo 的文档量不算小，单是 GitHub 上 doc 目录下的 Markdown 文件就有上百个，加上核心模块的头文件注释，文本量在几十万 Token 级别，本地做向量化索引和检索还挺吃资源的。

扣子的知识库直接解决了这些问题：文档上传云端自动分段索引，Bot 创建后生成一个链接，团队所有人共享。配置过程全部在浏览器里完成，不需要搭服务器，不需要写 Python 脚本，维护成本为零。

当然，代价也有。扣子是一个封闭平台，知识库的检索策略和模型选择只能在它的选项里挑，不能像本地方案那样精细调参。但对于比赛这个场景，开箱即用带来的效率优势远大于自定义空间的损失。

### 知识库搭建的关键环节

Apollo 的文档分布在几个不同的位置，我做了三件事来把它们整理成可用的知识库。

**第一，从 GitHub 拉取文档。** Apollo 仓库根目录下的 `docs/` 文件夹包含了官方的中英文技术文档，涵盖硬件搭建、模块介绍、API 说明等。这些文档大部分是 Markdown 格式，结构比较规整，最适合直接导入知识库。我用 git clone 拉到本地，然后筛选出 `docs/` 目录下的所有 `.md` 文件，剔除掉一些过时的版本说明，剩下大约 80 多个文档文件。除此之外，每个核心模块（planning、control、perception、prediction 等）的 `README.md` 也值得导入，它们包含了模块的整体架构说明。

**第二，处理代码注释。** Apollo 的 C++ 代码中有大量 Doxygen 风格的注释，很多关键的数据结构和接口定义都写在头文件的注释里。直接导入 `.h` 文件的话，绝大部分内容是代码，注释只占一小部分，对 Token 的浪费太严重。我的做法是写了一个简单的 Python 脚本，提取每个 `.h` 文件中的注释块和函数签名，拼成 Markdown 格式再导入。这一步有点繁琐，但效果很值——很多比赛里需要调用的 API 参数说明、数据结构定义，知识库都能直接回答出来。

**第三，分段策略选择。** 最初我用的是自动分段，结果发现效果不太稳定——Apollo 的技术文档经常包含代码块和表格，自动分段会在这些地方切得支离破碎，导致检索时匹配到的片段语义不完整。后来切换到按 Markdown 标题层级自定义分段，以二级标题（`##`）为分段的粒度，效果明显改善。比如 planning 模块的文档中，"Lane Follow Scenario"这样的小节可以被完整地作为一个检索单元。

### 模型选择与 Bot 配置

Bot 的人设我写得非常克制。没有写任何 Apollo 相关的领域知识——那些已经放在知识库里了。人设只约束行为：

- 基于知识库内容回答，不要编造
- 如果问题涉及具体代码函数，优先给出函数签名和所在头文件路径
- 当知识库检索不到相关内容时，明确告知，不要强行回答
- 回答中引用具体的文档来源

模型选的是 DeepSeek-V3。当时的原因是它在代码理解和中文技术文档上的表现比较均衡，而且 Token 成本相比豆包 Pro 要低不少。考虑到比赛期间队员每天要问几十上百个问题，成本也是一个不能忽视的因素。最终跑下来，DeepSeek 对 Apollo C++ 代码逻辑的理解没有出现过明显的偏差。

### 实际使用效果

这个知识库智能体在团队里用了一个多月，覆盖了几个典型场景：

- 新队员上手阶段，直接问"planning 模块的输入输出是什么"、"control 模块怎么配置 PID 参数"，五分钟就能搞清楚原来需要读两天文档才能弄明白的问题。
- 开发调参阶段，经常被问到"LateralOffset 这个参数在哪个文件定义的"、"LQR 控制器的状态矩阵维度是多少"这类具体问题，基本都能准确给出答案和代码路径。
- 排查问题时，把编译错误或运行时错误日志贴进去，Bot 能结合知识库里对模块的描述给出排查方向。

当然也有翻车的时候。Apollo 有几个核心模块的文档本身写得比较陈旧，版本更新后部分文档没有同步更新，Bot 检索出来的信息就和实际代码对不上了。这个问题的根源不在知识库也不在模型，而在原始文档的维护质量上。RAG 的上限始终被文档质量锁死，模型只是忠实地反映了好坏。

### 一点总结

用扣子搭这个知识库的整个过程，从开始到上线可用状态，前后花了大半天时间——其中一半时间花在文档的筛选和预处理上，真正的平台配置只用了两三个小时。对于比赛这种时间紧张的场景，这个投入产出比是完全可以接受的。如果你也需要处理一个大型开源工程的文档分析问题，值得一试。
