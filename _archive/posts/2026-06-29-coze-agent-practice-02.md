上一篇讲了怎么用扣子的知识库把 Apollo 开源工程的文档体系变成可检索的知识库智能体。这一篇说工作流——在比赛的中后期，纯问答式的知识库已经不够用了，我们需要 Bot 能主动做事，而不仅仅是回答问题。

### 为什么需要工作流

知识库 Bot 的工作模式很简单：用户提问 → 检索知识库 → LLM 生成回答。这个模式对于"某个参数在哪定义的"这类事实性问题很好用，但比赛中大量出现的是更复杂的需求：

- 用户问"帮我查一下 planning 模块里跟 Lane Follow 相关的所有代码文件"，这就需要知识库检索 + 代码仓库搜索两步操作。
- 用户贴了一小段代码问"这段配置有什么问题"，需要先在知识库里找到对应的配置文档，再做对比分析。
- 仿真跑完出了异常，用户想"帮我总结这轮的异常日志，并找出可能出问题的模块"，这涉及日志分析 + 知识库关联。

这些任务有一个共同点：它们不是单一的信息检索，而是多个步骤的组合。如果交给 Bot 自己去判断每个步骤该用什么工具，结果往往不可控——Bot 可能在需要查知识库的时候跑去搜网页，或者在一个步骤出错之后就卡住了。工作流就是来解决这个问题的：把流程固定下来，每个节点做什么、输入输出什么、异常了怎么处理，全部事先定义好。

### Apollo 比赛中的三个工作流

比赛期间我们根据实际需求搭了三个工作流，分别应对不同的开发阶段。

**第一个：代码快速定位工作流。** 这是使用频率最高的一个。它的流程是：

1. 用户输入一个自然语言描述（比如"我想找 planning 模块里处理十字路口的代码"）
2. LLM 节点把描述转化为关键词组合：从 Apollo 的模块命名规范中提取文件路径和模块名
3. 代码节点调用 GitHub API / 本地仓库索引，搜索匹配的文件路径和符号定义
4. 如果找到了，LLM 节点概括每个文件的功能；如果没找到，走降级分支提示用户换关键词

这个工作流帮助我们快速从一个模糊的功能描述定位到具体的代码文件。比赛的开发节奏很快，很多时候我们只知道"想要什么效果"而不知道"在哪改代码"，这个流程大大减少了逐层翻阅 Apollo 目录结构的时间。

**第二个：配置参数分析工作流。** Apollo 的模块参数分散在多个 proto 文件和 launch 文件中，参数之间的依赖关系和约束条件写在不同地方。这个工作流做的是：

1. 用户粘贴一个参数名或参数片段
2. 知识库节点检索参数的定义位置、取值范围和说明
3. LLM 节点分析参数与其他参数的关联关系（比如修改 A 参数时 B 参数必须同步调整）
4. 如果有已知的约束条件，一并返回；如果没有检索到约束，说明该参数是独立的

这个工作流的实用性在于：Apollo 的参数体系比较复杂，有些参数的约束写在文档里，有些写在代码注释里，还有一些只有社区讨论里提到过。知识库把它们全部收录之后，工作流负责整合输出。我们有好几次修 bug 就是靠这个工作流发现了一个参数的取值范围设错了。

**第三个：仿真日志智能分析工作流。** 比赛后期最头疼的问题是仿真环境中跑出来的异常日志——每次仿真会生成大量日志，逐条看效率极低。这个工作流的设计是：

1. 用户粘贴一整段仿真日志
2. LLM 节点做第一轮分析：提取日志中的 Warning / Error 级别条目，按时间线排列
3. 知识库节点检索每个错误对应的常见原因和解决方案
4. LLM 节点汇总生成一份诊断报告，按严重程度排序，附带建议的排查路径
5. 如果确认为已知问题，直接给出修复方案；如果是新问题，标注"未匹配到已知原因，建议手动排查"

这个工作流不是万能的——对于某些 Apollo 内核态的崩溃导致的段错误，日志分析根本拿不到有效信息。但对于大部分逻辑层的异常（配置错误、模块间通信超时、场景触发条件不满足），它的诊断准确率在 70% 以上，足以大幅减少手动排查的范围。

### 工作流设计中的教训

第一个教训：不要把流程设计得太长。我最初试着搞了一个"全链路分析"工作流——从用户输入一个场景描述，到分析代码、检查配置、对比仿真结果、输出修复建议，全部串在一个流程里。结果就是经常超时，而且一旦中间某个节点出错了，整个流程都要重跑。后来拆成三个独立的短流程，每个只做一件事，稳定性好得多。

第二个教训：代码节点的错误处理比预想的更重要。工作流里涉及到 GitHub API 调用的时候，网络问题导致的超时是最常见的失败场景。我们在每个代码节点后面都加了一个条件分支检查 error 变量，如果调用失败就跳过该步骤而不是终止流程。这个小改动大概省掉了 30% 的重试次数。

第三个教训：工作流的调试要比 Bot 的调试麻烦得多。扣子的工作流编辑器提供了节点级别的测试功能，但跨节点数据传递的问题只能靠手动跑完整流程来排查。变量命名一旦混乱，排查的难度直线上升。我们一开始没有注意变量命名规范，工作流的节点多了以后，经常出现上一个节点输出的字段名和下一个节点期望的字段名对不上的情况。后来我们定了个规则：所有节点的输出变量统一用 `snake_case` 加模块前缀，比如 `planning_file_list`、`log_analysis_summary`。这个习惯最好从一开始就养成。

### 多 Agent 协作的尝试

比赛末期我们试过扣子 3.0 的项目协作功能，建了一个项目，里面放三个 Agent：

- **文档 Agent**：绑定了第一篇里说的知识库，负责回答文档和代码相关的问题
- **日志 Agent**：绑定了仿真日志分析工作流
- **代码搜索 Agent**：绑定了代码定位工作流

理想情况是：队员提出需求，项目管理者把任务分配给不同的 Agent。实际用下来，这个分工的价值主要体现在职责隔离上——队员不用记三个 Bot 链接，在一个项目里 @ 对应的 Agent 就能干活。但也有明显的局限：Agent 之间没法自主协商，比如日志 Agent 分析出某个异常可能涉及 planning 模块的代码问题，它不能自己把任务转给代码搜索 Agent，需要人介入做中转。

所以这个阶段的多 Agent 协作，本质上还是人作为调度中心，Agent 作为专业工具。不过对于 Apollo 比赛这种需要多方向并行开发的场景，人+多个专业 Agent 的模式已经比单 Bot 模式提升了不少效率。至少队员不必在好几个 Bot 之间来回切，所有的消息链路收敛在一个项目里，这个改进是实实在在的。

### 总结

从最初的知识库问答 Bot，到后面三个专用工作流，再到项目级别的多 Agent 协作，这套东西贯穿了我们参加 Apollo 比赛的整个过程。说它是"夺冠的关键"有点夸张——最终的解决方案还是要靠人写代码和调参数。但它确实帮我们省下了大量翻文档、搜代码、查日志的时间，让整个团队的开发节奏快了不少。对于一个四人团队的比赛来说，这个效率提升可能恰恰是最关键的变量。
